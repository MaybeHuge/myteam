# SeaweedFS 资源存储验证

日期：2026-10-27。范围：用户明确要求使用 SeaweedFS，并移除 LocalStorage；本次不推进其他业务任务。

## 实现与配置

应用资源存储统一使用 S3Storage，通过 AWS SDK v3 访问 SeaweedFS。LocalStorage 源码、依赖入口及 STORAGE_PATH 配置已移除；共享内容校验独立放在 attachment-file.ts。后端保留项目/对象权限、CSRF、幂等、文件大小与格式检查，图片和其他附件使用同一存储。

SeaweedFS 固定 4.51，本机运行官方 Linux x64 二进制，发布包 SHA-256 为 `c03be37416a8ee672c77766e20b22a4e1430744c3af2668599a4b6eeaec14cee`。S3 监听 127.0.0.1:8333，其他组件同样仅本机可达，未启用匿名 S3 访问；本地服务停启与桶初始化均已实际执行。

配置使用 S3_ENDPOINT/REGION/BUCKET/ACCESS_KEY_ID/SECRET_ACCESS_KEY/FORCE_PATH_STYLE/PREFIX。本机 .env 已配置并保留原有账号/数据库配置，文档不记录访问密钥。Compose 提供持久卷和认证配置，当前 WSL 没有实际执行 Docker Compose，因此不将其算作已验证部署。

第五个数据库迁移新增 Attachment.storageBucket；新上传记录始终保存桶与完整对象键，现行业务库无未迁移记录。远端上传在业务事务外，提交前复查权限。明确回滚补偿删除、补偿失败延后清理、提交结果不明保留对象，细节见 [ADR-004](../adr/004-seaweedfs-resource-storage.md)。

## 实际迁移与持久性

切换前查到业务库已有 2 份附件。运行 storage:migrate-local，按原大小/SHA-256 校验，上传后回读再校验，更新桶与对象键，保留附件 ID、业务关联、原文件名、上传人、时间和原始文件。

通过本地原业务 API 登录后，逐份调用原附件 ID 的下载地址，实际字节及 SHA-256 均匹配。随后停止并重新启动 SeaweedFS，再经原 API 完整下载 2 份资源，校验仍全部通过。没有通过删除/重新创建业务附件来完成切换。

原始文件保留在 .local/uploads；本机 .local/seaweedfs-migration-manifest.json 保存原键与现行引用的映射，不入库。该留存用于本次迁移追溯，不是运行时存储回退。完整备份恢复演练仍未执行。

- 完整 check:ci 退出码 0，共 79 项自动化检查通过；日志位于 .local/seaweedfs-ci.log。
- 契约 7 项；静态、类型及生产构建通过，保留已有前端公共块大小提示。
- 集成 67 项，均连接真实 PostgreSQL 与 SeaweedFS，使用独立的 `-test` 桶和每批唯一 tests/ 前缀。
- 浏览器 5 项，包括项目/迭代原流程及中文附件上传下载、通知、权限与窄屏协作。实际上传下载经过 S3。

新增或扩展场景：

- 并发同键上传只保留一份对象/附件引用，重试及不同输入按幂等规则处理。
- 上传前授权与上传后提交前授权；上传过程中角色收回时，禁止落库并清理暂存对象。
- 断言 S3 上传发生在数据库事务外，避免网络操作占用项目锁。
- 模拟数据库提交已成功但客户端丢失结果，保留原对象；同键重试返回原 ID 并清理额外暂存对象。
- 使用真实错误凭据访问 SeaweedFS：上传及就绪返回 503，存活检查仍可用，不产生附件记录，不返回凭据。
- 审计/通知故障仍整体回滚；补偿删除故障保留原错误，对象能由清理流程回收。
- 孤立清理保护近 24 小时及有引用对象，只扫描当前桶/前缀；删除前查询最新数据库引用。
- 匿名 S3 下载被拒绝，应用的非成员/跨项目/只读/关闭状态及上传校验继续通过。

本地检查日志位于 .local/seaweedfs-integration.log、.local/seaweedfs-e2e.log，不入库。
