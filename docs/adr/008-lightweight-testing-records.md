# ADR-008：任务三状态与测试记录

日期：2026-10-28。状态：已实现。用户明确要求简化任务和测试流程，且旧提测、执行、缺陷历史无需保留。本决策替代 ADR-007 中提测、批次和任务测试状态的规则；需求评审、用例修订及版本构建能力继续使用。

## 任务与需求

任务公开状态为 TODO（待开始）、IN_PROGRESS（进行中）、COMPLETED（完成）。负责人自行开始、完成、重新开始或退回待开始；具有任务管理权限的成员可代操作。阻塞仍是独立标记。完成任务同步 WorkItem.DONE，重新开始同步 OPEN。

需求继续保留草稿、评审、确认流程。确认后的状态按以下顺序计算：

1. 没有有效任务或所有任务待开始：已确认。
2. 部分任务开始或完成：实现中。
3. 至少一个有效任务且全部完成、没有本轮测试记录：待测试（沿用 ACCEPTING 存储值）。
4. 任务全部完成且已创建本轮记录，但当前范围尚未全部通过：测试中（TESTING）。
5. 当前关联的全部未废弃用例均为可使用修订、各自本轮最新记录通过，且无未解决的严重/致命缺陷：已完成，同时 WorkItem.DONE。

无任务、无用例、用例未通过评审或未执行都不能被算作完成。这里的完成是本次约定的开发测试完成，不表示已发布。独立业务验收和发布仍属于后续规划，不再作为当前需求完成的必经入口。

创建新任务、重新开始或退回任务会递增需求 testCycle，使原测试结果失效。需求修订递增内容修订、范围及测试轮次，并把已完成任务重新置为进行中；旧依据须重新确认并由开发核对。修改用例会使原用例修订的通过结果失效。缺陷失败不会自动重开已完成的开发任务。

## 测试记录

移除提测管理、测试执行页面及其接口。测试记录从项目测试记录页或具体用例发起，属于一个需求、一条用例及其修订、一次需求测试轮次。多需求共享用例必须明确本次验证的需求。

迭代关闭后仍可为其需求创建测试记录、提交测试结果及进行缺陷复测。测试操作按实际结果继续汇总需求状态，迭代保持已关闭状态，并保留原关闭时间与总结；项目写入权限、需求与用例依据有效性等校验继续适用。

TestRecord 保存需求修订、轮次、用例完整 v1 快照、环境、可选构建、执行人、实际表现、附件和时间。类型为 INITIAL/RETEST，结果为 NOT_RUN/PASSED/FAILED，复测不是结果值。页面据此显示待测试、通过、未通过、待复测及复测结论。用例列表展示最近有效测试记录的结果，需求完成始终按该需求的本轮范围计算。

记录创建后允许上传截图及其他支持的附件。提交最终结果时校验附件属于该记录及当前项目；已完成结果不可覆盖，后续测试另建记录。当前需求或用例依据失效的记录只供查询，不能继续提交。单个需求/轮次/用例修订只能有一条待填写记录。

版本只修改名称或说明时，范围版本不递增，也不使测试记录或构建失效。真正增删关联需求或任务时，范围版本递增，相关测试依据仍按现行规则失效。此前已失效的历史构建不会自动恢复。

## 缺陷

手工报告缺陷可以不关联用例、测试记录或构建。关联记录会自动关联其用例，且所有证据必须属于当前项目、符合缺陷需求。DefectCaseLink 和 DefectRecordLink 为独立多对多关系。

测试未通过时，先使用显式选择的缺陷或该场景已有未解决缺陷，否则同事务自动创建缺陷，带入复现、预期、实际和环境。缺陷处理人优先使用指定人，其次使用需求任务负责人；均校验成员权限。重复保存同一命令不会重复创建缺陷。

提交修复后，新建对应复测记录。关联缺陷待复测时，复测通过关闭，未通过重新打开；修复前建立的记录不得充当修复后的证据。有构建上下文时，修复必须提供新构建，复测必须使用实际修复构建。没有关联用例的手工缺陷可直接登记复测结论，但必须有原因和证据。开发权限不能代替复测权限。

严重/致命缺陷阻止需求完成；重复缺陷跟随主缺陷判断，不允许循环。普通/轻微缺陷可延期，延期不表示已修复。

## 数据与一致性

所有变更继续复用项目行锁、授权、乐观版本、幂等键及事务事件。测试记录和缺陷关联使用项目复合外键；记录身份、快照和已完成结果由数据库触发器保护。附件继续使用 SeaweedFS 私有 S3 桶及下载授权。

待复测缺陷的修复构建因版本范围变更失效时，开发负责人可选择实际包含修复、且属于当前需求与版本范围的新构建。操作保留处理历史；测试人员随后基于新构建重新发起复测。已有有效待填写复测记录时，须先完成该记录。
