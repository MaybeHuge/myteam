# ADR-005：需求基线修订与下游依据失效

日期：2026-10-27。状态：M2 实施。关联任务：M2-04；M3/M4/M5 继续接入同一契约。

## 背景与选择

需求确认后仍可能改变业务范围和验收标准。直接覆盖已确认内容会使旧测试、验收及发布检查看起来仍然有效。当前尚未实现后续完整模块，因此先提供实际运行的修订流程、持久影响记录和可复用的有效性校验契约，不提前建立虚构的验收或发布记录。

Requirement 维护内容 revision、最近已确认 acceptedRevision、影响代次 scopeVersion，以及命令并发 version。评审记录保存每轮快照；RequirementChange 追加保存修订发起前的已确认快照、新草稿快照、原因、影响、操作者、任务范围及失效标记，数据库禁止更新记录。

## 修订与任务

已确认/实现中的需求通过 revise 命令发起新草稿，要求原因、影响说明及实际内容或责任计划变化。新草稿必须重新评审，旧评审及确认基线仍可读取。发起修订递增 scopeVersion，向关联任务负责人和协助人通知，并递增未结束任务 version，让旧卡片命令发生并发冲突。

运行中任务记录开始/核对时的 basisRevision。需求修订期间不能据旧基线恢复；重新确认后，任务负责人需要明确核对具体 requirementRevision 并说明影响结论，再恢复原有阻塞。核对不自动清除阻塞。任务业务状态、独立阻塞标记及需求依据分别保留。

## 下游接入契约

RequirementValidity.capture(tx, projectId, ids) 只捕获已确认且内容与 acceptedRevision 一致的范围，返回 requirementId/revision/scopeVersion。下游模块将此令牌与自身证据一起保存；执行相关资格判断时，必须在授权事务内调用 assertCurrent，并与业务写入处于同一项目锁和事务。

旧令牌在修订发起时立即无效，重新确认、退回、撤回或修改草稿都不会使其复活。RequirementChange.effects 持久标明用例需复审、验收及发布检查依据失效，供后续模块追溯和处理。当前没有公开创建或修改“验收/发布证据”的接口，也没有声称后续模块已经完成。

M3 的用例复审、M4 的测试范围以及 M5 的验收/发布检查应调用这一契约，不能仅比较需求标题、通知是否已读或当前状态字符串。真实模块接入后的完整链路仍需对应阶段验收。

## 一致性与验证

修订、任务版本、影响记录、审计、去重通知及幂等同事务。资格捕获/校验使用同一项目行锁协调修订，不能先在事务外检查后再写入。集成检查验证旧令牌失效、重新确认不恢复旧依据、跨项目拒绝、并发修订、事务回滚及原评审快照不变。

## M3-01/02 接入结果

TestCaseRevision 在内容保存时捕获完整需求令牌；送审、通过和 selectUsableRevision 在项目事务锁内调用 assertCurrent。需求 revise 同事务标记关联未废弃用例 needsReview 并增加 version，包括评审中用例，阻止旧页面给出新结论。重新确认需求不清除此标记；需保存新内容修订并重新通过。旧用例修订和历史评审继续保留，不能选择旧修订替代当前待评审内容。

此接入完成了真实用例失效及重审规则。覆盖提示、复查工作台、执行快照及实际批次选择仍按 M3-03/04、M4 推进；验收和发布仍按 M5 接入。

## M4 接入结果（2026-10-28）

M4 已复用内容修订与 basisVersion 校验提测、选择、执行和复测。需求进入 ACCEPTING 不改变确认依据；修订仍使批次不能继续记录或完成，但可以取消并查询旧历史。版本范围修订使就绪任务回开发。M5 验收/发布继续接入同一令牌。验证见 [M4 完成记录](../verification/m4-completion.md)。
