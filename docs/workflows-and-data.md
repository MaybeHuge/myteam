# 业务流程与数据设计

更新日期：2026-10-28。现行基线为 [ADR-008](adr/008-lightweight-testing-records.md)，替代原提测单与测试批次流程。

## 1. 日常流程

1. 产品创建需求、指定负责人和验收标准，提交评审并确认。
2. 开发拆任务、估算、分配或认领，维护待开始、进行中、完成状态。
3. 测试与开发并行准备和评审用例，需求可以关联多个用例，用例也可复用到多个需求。
4. 全部开发任务完成，需求自动进入待测试。
5. 从用例或测试记录页开始一次测试，明确需求和环境，可引用版本构建。
6. 上传截图或其他附件，记录实际表现并提交通过或未通过。
7. 未通过自动创建或复用缺陷。开发修复后，测试新建复测记录，失败重开、通过关闭。
8. 本轮全部用例通过且无阻断缺陷，需求自动完成。发布仍在后续版本流程中单独登记。

## 2. 当前状态

| 对象     | 主流程                                                     | 分支                                                            |
| -------- | ---------------------------------------------------------- | --------------------------------------------------------------- |
| 需求     | 草稿 → 待评审 → 已确认 → 实现中 → 待测试 → 测试中 → 已完成 | 退回/撤回回草稿；修订重新评审；新增开发工作或缺陷使进度重新计算 |
| 任务     | 待开始 → 进行中 → 完成                                     | 可重新开始、退回待开始；阻塞为独立标记                          |
| 用例     | 草稿 → 待评审 → 可使用 → 已废弃                            | 内容修订重新评审；测试结果来自测试记录                          |
| 测试记录 | 待测试 → 通过 / 未通过                                     | 测试类型独立区分首次测试和复测；新测试新增记录                  |
| 缺陷     | 待确认 → 待修复 → 修复中 → 待复测 → 已关闭                 | 复测失败回待修复；支持重开、重复、非缺陷、无法复现和延期        |

任务表示开发进度。需求表示整体开发测试进度。任务全部完成前，即使提前测试通过，需求也不能完成。没有任务或用例不满足完成条件。

需求的“待测试”沿用 ACCEPTING 存储值，新增 TESTING 表示测试中。需求已完成同步 WorkItem.DONE；重开时同步 OPEN，迭代关闭仍以真实未完成工作项拦截。

## 3. 关键规则

- 开始任务须有当前已确认需求、负责人、可写项目与有效计划。完成任务还要求需求依据有效且未阻塞。
- 任务由本人负责或具有任务管理权限的成员操作，不能直接更新任意 status 绕过规则。
- 已完成任务重新开始、新建任务会使旧测试轮次失效。需求修订使旧测试依据失效，相关已完成任务回进行中并重新核对影响。
- 当前需求所有未废弃关联用例构成必测范围，包括尚未通过评审的用例；不能通过漏选用例提前完成需求。
- 多需求共享用例的记录按需求隔离。旧需求修订、旧测试轮次或旧用例修订的通过记录不参与当前完成判断。
- 首次失败自动建缺陷；重复失败优先关联原未解决缺陷。一个缺陷可关联多个用例和记录，一条记录也可关联多个缺陷。
- 手工缺陷的用例、记录和构建关联均可选；选了记录就自动带出其用例。跨项目或不同需求的证据会被拒绝。
- 修复与复测必须有说明；已有构建上下文时必须继续引用实际修复构建。复测记录须在修复提交后创建且为当前有效场景记录。
- 严重/致命未解决缺陷阻止需求完成。重复问题按主缺陷判断，延期不能当作已修复。
- 最终测试结果不能覆盖；记录快照和身份不可改写。截图和文件属于具体记录，不能引用其他记录的附件。
- 所有操作保留授权、项目锁、版本号、幂等与事务日志；旧通知不会成为当前待办。

## 4. 数据关系

| 实体                                                | 主要关系                                                     |
| --------------------------------------------------- | ------------------------------------------------------------ |
| Requirement / RequirementReview / RequirementChange | 当前需求、评审基线、修订与测试轮次                           |
| Task / WorkItem                                     | 需求下的开发工作，领域状态和计划处理结论同事务更新           |
| TestCase / TestCaseRevision / TestCaseReview        | 可复用场景、内容修订与评审                                   |
| RequirementCaseLink                                 | 需求和用例的多对多关联                                       |
| TestRecord                                          | 一个需求、用例修订、测试轮次的一次测试，包含快照、结果及证据 |
| DefectCaseLink / DefectRecordLink                   | 缺陷与用例、记录的独立多对多关联                             |
| Defect / DefectDisposition                          | 问题、责任、修复、复测和特殊处理历史                         |
| Release / ReleaseItem / Build                       | 版本范围及可选的构建上下文，发布能力仍待后续接入             |
| Attachment / Comment                                | 项目、需求、任务、用例、测试记录、缺陷及版本的授权协作       |
| ActivityLog / Notification                          | 事务审计和站内消息                                           |

当前数据库仍保留旧流程的空表供后续结构整理，旧路由和页面已移除，不读取或兼容旧测试历史。用户授权的清理范围及状态映射见 ADR-008。

## 5. 工作台

工作台展示当前任务、需求/用例评审、需求变化复查、待填写测试记录、缺陷确认/修复/复测及延期跟进。记录失效、结果提交或责任改变后，待办随真实状态更新。成员停用或失去相关角色前需要处理未完成责任。

## 6. 后续范围

业务独立验收、发布检查、发布/回滚、生产验证及复盘仍需后续设计。它们应引用当前测试记录和缺陷条件，不恢复旧提测单或批次门槛。需求完成不等同于版本已发布。
