# MyTeam 详细开发计划

版本：0.1；基线日期：2026-10-27。  
当前基线：任务与测试流程已按 ADR-008 简化，需求完成不再等待独立验收入口。下列阶段表保留原规划；其中提测、测试批次与七状态任务已被测试记录和三状态任务替代。后续验收及发布必须按现行模型重新安排。实际证据与边界见 [M4 完成验证](verification/m4-completion.md) 及 [进度台账](progress.md)。  
配套文档：[需求基线](requirements.md)、[技术架构](architecture.md)、[流程与数据](workflows-and-data.md)、[验收清单](acceptance.md)、[进度台账](progress.md)。

## 1. 实施目标与原则

首期交付可以真实使用的最小完整闭环：创建项目和迭代、确认需求、分配任务、准备测试用例、提交测试、发现并修复缺陷、复测、业务验收、登记发布及上线验证、复盘归档。

实施原则：

1. 按业务纵向交付：一个任务同时考虑页面、接口、权限、数据和验证，避免前端全部完成后再补业务逻辑。
2. 所有关键状态由服务端控制，前端提供允许的操作和明确反馈。
3. 用例管理在首期实现，发生在需求确认后，与开发并行。
4. 历史记录、测试快照、权限、并发冲突作为基础能力实现，不能留到上线后补。
5. 首期发布能力为人工登记和条件检查，自动执行构建、测试、部署放到工具集成阶段。
6. 每个任务有稳定编号、依赖、交付物和验收条件；只有实际验证通过后才可标记完成。

| P4-03 | 规模化   | 跨项目报表、容量及运维增强             | 按确认规模完成性能与恢复验证                 |

## 12. 每个开发任务的完成定义

1. 需求范围清楚，接口、数据、页面与权限行为一致。
2. 涉及状态的实现满足对应 BR 规则，事务和并发行为明确。
3. 实际验证正常流程、至少一个关键失败分支及权限边界；记录证据。
4. 核心业务不以浏览器本地存储或静态演示数据代替服务端持久化。
5. 涉及数据结构时提交迁移及兼容说明，涉及配置时更新示例及启动说明。
6. 无阻断缺陷；剩余问题登记为独立任务，不以注释代替跟踪。
7. 更新进度台账、验证记录和必要设计文档；标记完成与实际结果一致。

## 13. 测试与验证策略

- 优先自动化覆盖：权限隔离、状态机、发布门禁、历史快照、并发冲突、重复请求、关联一致性。
- 接口集成测试覆盖一次完整缺陷循环及版本发布检查；采用隔离测试数据库或等效环境。
- 关键页面端到端验证覆盖角色切换、提测、失败建缺陷、复测、验收和发布。
- 视觉与文案等低影响变更采用人工检查，不建立仅重复实现的无效测试。
- 测试结果记录执行环境、应用版本、数据准备和证据；示例或计划不当作实际通过。
- 测试清单与具体任务对应关系见 docs/acceptance.md，发生需求变更同步修订。

## 14. 变更与持续推进

- 任务状态统一为：待开始、进行中、待验证、已完成、阻塞、取消。
- 每次开始先检查依赖；未开始开发前可以调整顺序，但不能绕过业务依赖。
- 阻塞记录原因、需要的输入、负责人、下一次处理动作，不只写“待处理”。
- 新需求先登记 CHG 编号，评估范围、数据、权限、用例、工作量和版本影响，再更新计划。
- 首期新增内容优先通过替换或后移控制范围，确有必要再调整工作量。
- 重要决策使用 ADR 编号，记录上下文、方案、取舍和生效任务。
- 不自动创建周期任务、发送团队消息或部署系统；这些动作需要实际任务授权。
